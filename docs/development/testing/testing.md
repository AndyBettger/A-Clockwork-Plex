# Testing A Clockwork Plex

Use the project virtual environment rather than bare system `python3`, because the dashboard/runtime dependencies are intentionally installed into the project environment.

## Normal local validation

From the repository root:

```bash
bash scripts/run-tests.sh
```

The runner selects, in order:

1. the currently activated virtual environment;
2. `venv/bin/python`;
3. `.venv/bin/python`.

It requires Flask in the selected environment and Node.js for JavaScript syntax validation. It then performs the maintained local validation sequence:

1. compile every Python source under `app/` and `scripts/`;
2. run `bash -n` against `setup.sh`, `appliance-installer.sh` and every shell script under `scripts/`;
3. run `node --check` against every JavaScript file under `app/static/js/`;
4. run the complete Python unit/regression suite.

Python bytecode generated by the compile pass is redirected to a temporary cache root so the validation command does not dirty the repository checkout.

## Run the Python suite directly

```bash
venv/bin/python -m unittest discover -s tests -v
```

To install or refresh dependencies in the project environment:

```bash
venv/bin/python -m pip install -r requirements.txt
```

## CI relationship

`.github/workflows/tests.yml` is the release CI authority. It performs the same core compile/syntax/unit-test gate and additionally carries targeted early assertions for critical page wiring and release contracts.

A green local `scripts/run-tests.sh` result is useful before committing, but the corresponding GitHub Actions run must also pass before a release-hygiene checkpoint is recorded green.

## Safety

The unit suite uses fakes, temporary roots and explicit test boundaries for mutating installer/audio operations. It is not a substitute for the separately recorded replacement-SD physical acceptance sequence in `docs/final-clean-room-physical-progress-2026-08-21.md`.
