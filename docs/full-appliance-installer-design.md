# Full appliance installer and multi-node weather design

**Status:** Phase 7 design and source integration in progress  
**Started:** 10 August 2026  
**Branch:** `feature/alarm-engine`

## Goal

A Clockwork Plex should be installable as a complete Raspberry Pi appliance rather than reconstructed from a remembered sequence of component scripts. The top-level installer is an orchestrator: it owns the sequence, selected capabilities and final verification, while specialist components retain authority for their own subsystem.

This is especially important for repeatable multi-appliance deployment. A second, third or replacement clock should be reproducible from the same installer inputs without copying machine-specific state or teaching a new installer a second version of the audio graph.

## Installer authority

The intended entry point is the repository-root `install.sh`.

The Phase 7 implementation remains deliberately **plan-only**. It accepts the future repeatable choices and reports the intended component graph, but `--apply` is blocked until the component boundaries and rollback rules are implemented and tested.

Initial profile arguments:

```text
--audio direct|eq
--weather-observations ecowitt-push|weather-underground
--non-interactive
```

The top-level installer must not become another implementation of audio routing. For EQ-capable audio it will call the accepted `scripts/audio/*` lifecycle. Direct audio is a first-class profile and now has its own alarm-safe component boundary rather than making the older `scripts/install-shared-audio.sh` a competing authority.

The current component inventory shows mixed generations of installer style. `install-dashboard-service.sh` and `install-dashboard-kiosk.sh` already use check-first guarded activation, while several older helpers install immediately. Phase 7 should wrap or refactor those components behind one consistent top-level plan/apply contract instead of blindly chaining them together.

## Intended fresh-Pi sequence

```text
A Clockwork Plex installer
  1. prerequisite / hardware / OS checks
  2. application files and Python requirements
  3. dashboard service
  4. Shairport Sync integration and lifecycle hooks
  5. AirPlay metadata listener
  6. alarm-audio and managed helper permissions
  7. selected audio profile
       direct
       or EQ-capable -> accepted scripts/audio lifecycle
  8. selected weather-observation provider
  9. dashboard kiosk startup
 10. appliance-level verification report
```

The exact ordering may be refined as dependencies are made explicit, but each subsystem should have one owner and a verifiable post-condition.

## Direct audio component boundary

Phase 7 exposed an important distinction between the historical pre-EQ rollback baseline and the Direct profile a fresh appliance should actually use.

The historical route with SHA-256:

```text
08d000933e132af4fe0d66f1f80fd6ba08d15398b98f5ea986f69709139e74b9
```

is exactly the ALSA route generated by the older `scripts/install-shared-audio.sh`. In that route, `acp_alarm_volume` feeds `acp_master`, so Music Master also controls alarm audio. That route remains valuable as the exact physically accepted Phase 6 uninstall target for the already-installed bedroom Pi, but it does **not** satisfy the settled appliance rule that scheduled alarms bypass Music Master.

The fresh-appliance Direct profile therefore uses the already physically proven alarm-safe direct route with SHA-256:

```text
654ff170e6a009d50fa7494500ca930093aa22ab6cd10a606a7d7fe14d0493c9
```

Its graph is:

```text
Plexamp -> Plexamp trim --\
                          +-> Music Master -> stereo dmix -> DAC
AirPlay -> AirPlay trim --/
Alarm -> Maximum Alarm Volume -----------> stereo dmix -> DAC
```

The exact proven file is now also materialised at `installer/profiles/direct/alarm-safe.conf`. `installer/lib/direct_audio.sh` is currently a read-only component contract: it validates that exact checksum, identifies the common mixer/Plexamp/Shairport integration responsibilities and prints the plan, but deliberately contains no activation path.

This creates one Phase 7 integration issue that must be solved explicitly rather than hidden. The accepted standalone EQ first-install path still validates the historical `08d00093...` direct baseline. A fresh appliance should start from the alarm-safe `654ff170...` Direct profile instead. Phase 7 must therefore generalise or bridge the EQ install-baseline contract under non-production tests before the top-level installer can enable `--apply`. The existing bedroom Pi and its accepted Phase 6 lifecycle are not changed merely to solve that fresh-install problem.

## Weather architecture for several clocks

### Existing split of responsibilities

The application separates two weather jobs:

- **observations** provide the local/current station readings displayed on the Clock and Weather pages;
- **forecast** uses the independent Open-Meteo service and cache.

That separation is preserved. Changing the observation source does not replace the accepted Open-Meteo forecast service.

### Problem with local Ecowitt custom push

The current `ecowitt_push` path is suitable for the existing clock because the weather station can send its custom local-network upload to that appliance. It does not scale cleanly when the station can target only one local destination.

The multi-appliance solution does **not** introduce a new always-on local weather fan-out/cache server. Each clock can instead obtain current observations independently from a supported upstream provider.

### Supported observation providers

#### `ecowitt_push`

Keep the current provider for installations where the station can push directly to that clock. This remains the default during the migration so existing installations do not change behaviour unexpectedly.

In production composition the established `/api/weather/ecowitt` URL is promoted to use the same observation-storage function as remote polling. The public URL and response contract remain intact; the change removes duplicate state-writing logic rather than adding another weather owner.

#### `weather_underground`

Weather Underground PWS is the first remote-pull provider. The station ID is normal configuration, while the API key is referenced by environment-variable name and is not written into `config.json` or returned through normal settings/status payloads.

`app/weather_observations.py` now owns the remote polling lifecycle. Its `WeatherObservationService`:

- is passive when `weather.provider=ecowitt_push`, so the existing station push remains authoritative;
- polls the configured Weather Underground PWS only when that provider is selected;
- reads the API key at runtime through the configured environment-variable name;
- bounds refresh, stale and timeout settings;
- reports pending, ready, degraded, stale, configuration-required and credentials-required states without returning the key or request URL;
- maps the current PWS response into the established dashboard weather-key vocabulary;
- runs as one owned background worker from `app/runner.py` and exposes `/api/weather/observations` for public health and deliberate refresh.

The mapper requests imperial PWS values because the existing dashboard key contract already distinguishes Fahrenheit, mph and inch-based precipitation. Weather Underground's current `pressure` value is mapped to the existing `baromrelin` key. That is important: `baromrelin` is already recognised by the dashboard as an inHg source, so both the displayed pressure and pressure-history/barometer path convert it correctly. The earlier provisional `pressurein` key was removed because the dashboard did not recognise it.

`app/weather_observation_store.py` is the single production storage contract for both providers. It replaces the current observation, records the receipt time, updates daily extremes, updates pressure history and persists `state.json`. It also strips sensitive/empty fields before persistence. Provider code therefore maps upstream data but does not own a second copy of dashboard weather state.

Remote PWS observations will not necessarily contain every field supplied by an Ecowitt local upload. In particular, indoor readings and Ecowitt-specific sensor/battery fields may be absent. The UI should show unavailable data as unavailable rather than synthesising it.

#### Met Office WOW

Do not add WOW as a new production dependency. The Met Office has announced retirement of the Weather Observations Website during 2026, so building a new multi-appliance observation path around it would create a near-term migration problem. Existing station uploads to WOW may continue while the service remains available, but A Clockwork Plex should not depend on it for its new remote observation mode.

## Pressure history / barometer

The dashboard already maintains its own persistent local pressure history and uses an approximately three-hour comparison for the barometer trend. That mechanism remains useful regardless of provider. A normal reboot does not inherently require the barometer to relearn from zero because the history lives in `state.json`; the warm-up issue is mainly a brand-new appliance, lost state or deliberately cleared history.

Every successful Weather Underground current-observation poll now contributes the current station pressure to that same history through the shared store.

Weather Underground's documented PWS recent-history products were reviewed before implementing any bootstrap. The rapid one-day and hourly seven-day products expose pressure fields such as `pressureMax`, `pressureMin` and `pressureTrend` for each historical record rather than the same instantaneous `pressure` field returned by the current-observation endpoint. Those values are useful aggregates, but they are not a sufficiently clear like-for-like source from which to fabricate the exact historical pressure points expected by the existing barometer algorithm.

Therefore Phase 7 currently **rejects automatic pressure-history seeding from those documented aggregate fields**. The safe behaviour is:

1. preserve existing local history across normal restarts;
2. append every successful current PWS pressure reading;
3. allow a new/empty installation to warm up naturally if no trustworthy sample history is available.

A real response from the user's own station may still be inspected when credentials are available, but code will not reinterpret aggregate fields as instantaneous pressure merely to make the graph look populated.

No shared local cache server is required; each appliance owns only its small local display/history cache.

## Configuration and unified Settings

Example shape:

```json
{
  "weather": {
    "provider": "weather_underground",
    "weather_underground": {
      "station_id": "YOUR_STATION_ID",
      "api_key_env": "WEATHER_UNDERGROUND_API_KEY",
      "refresh_seconds": 60,
      "stale_seconds": 300,
      "request_timeout_seconds": 8,
      "pressure_history_hours": 6
    },
    "forecast": {
      "provider": "open_meteo"
    }
  }
}
```

The real API key belongs in the service environment or a root-managed environment file, not in the example or committed configuration.

`app/weather_observation_settings.py` now supplies the revisioned public/submitted configuration contract used by unified Settings. It permits provider, station ID, environment-variable name and bounded timing settings, while explicitly rejecting attempts to submit an API key/password/token/secret through normal Settings. The production Settings service also reports observation-service health and wakes/refreshes the provider when that configuration changes. Browser controls for choosing/editing the observation provider are still to be added; the backend transaction/status contract exists first so the UI will not invent another authority.

### Checkpoint 2 — observation runtime and shared state

Completed in source/tests:

- owned Weather Underground polling service and public health endpoint;
- runtime API-key lookup without normal config/status exposure;
- correct current-pressure mapping into the existing barometer vocabulary;
- one production observation-storage authority for Ecowitt push and Weather Underground polling;
- runner start/shutdown ownership;
- revisioned unified Settings backend configuration/status contract;
- direct history-API review rejecting unsafe aggregate-to-instantaneous pressure reconstruction.

No Phase 7 change in these checkpoints has been deployed to the bedroom Pi. `install.sh --apply` remains deliberately blocked.

### Checkpoint 3 — Direct profile boundary

Completed in source/tests:

- exact physically proven alarm-safe direct route materialised as the Direct profile;
- read-only Direct component validation/planning library;
- top-level Direct plan reports that alarm bypasses Music Master;
- legacy `08d00093...` route identified as a historical EQ uninstall baseline, not the future Direct profile;
- fresh-EQ baseline mismatch exposed explicitly as a pending integration gate rather than silently reusing the wrong alarm semantics.
